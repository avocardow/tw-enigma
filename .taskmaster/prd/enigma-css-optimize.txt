# Enigma Core Command Implementation - Product Requirements Document

# Overview
The **main `enigma` command** functionality is completely missing from the CLI. While the core CSS optimization engine is implemented in packages/core, there is no primary command that exposes the essential tw-enigma pattern consolidation workflow that users expect as the core product functionality.

**Problem Solved:** The tw-enigma ecosystem has:
✅ Comprehensive CSS optimization engine (packages/core)
✅ Scramble integration capabilities (when scramble package exists)
✅ Supporting commands (css-config, init-config, template, etc.)
❌ **MISSING: The main `enigma` command** that performs pattern consolidation

**This is the primary value proposition of tw-enigma** - converting patterns like `"top-0 z-50 w-full border-b border-gray-200/40 bg-background/95 backdrop-blur supports-[backdrop-filter]:bg-background/60"` into short identifiers like `"kqqygl"` with corresponding CSS generation.

**Target Users:** All tw-enigma users who want to optimize their Tailwind CSS by consolidating repetitive class patterns.

**Value Proposition:** The core command that performs pattern analysis, generates short identifiers, creates CSS with @apply directives, and rewrites asset files - the fundamental purpose of tw-enigma.

# Core Features

## 1. Main Enigma Command
**What it does:** Performs complete CSS pattern optimization workflow
- Analyzes HTML/JS files for Tailwind class patterns
- Generates short identifiers for frequent patterns
- Creates CSS with @apply directives
- Rewrites asset files with consolidated classes
- Integrates with Scramble when available
**Why it's important:** This IS tw-enigma - the core functionality users install the package for
**How it works:** Single command that orchestrates the entire optimization pipeline using existing core engine

## 2. Build Integration Workflow
**What it does:** Seamlessly integrates pattern optimization into build processes
- Discovers build output directory automatically
- Processes HTML and JavaScript files
- Generates and injects optimized CSS
- Handles file integrity and backups
**Why it's important:** Zero-configuration optimization that works with any build tool
**How it works:** Uses existing file discovery and processing logic from packages/core

## 3. Scramble Integration Pipeline
**What it does:** Automatically integrates with @tw-enigma/scramble when available
- Detects scramble package presence
- Builds scramble with user configuration
- Injects scramble script into HTML files
- Coordinates optimization + scrambling workflow
**Why it's important:** Seamless integration between optimization and visual scrambling effects
**How it works:** Follows the integration sequence defined in scramble PRD

## 4. Configuration and Customization
**What it does:** Accepts comprehensive configuration for optimization behavior
- Pattern frequency thresholds
- Output file locations
- Custom identifier naming strategies
- Scramble integration settings
**Why it's important:** Flexible optimization that adapts to different project needs
**How it works:** Uses existing configuration system from packages/core

# User Experience

## Primary User Flow (Core Command)
```bash
# Basic optimization
enigma

# With configuration
enigma --build-dir dist --output-css assets/enigma.css

# With scrambling effect
enigma --scramble --scramble-speed 100

# Dry run mode
enigma --dry-run --verbose
```

## Integration with Existing Commands
```bash
# Setup and configuration
enigma css-config --preset production

# Main optimization (NEW)
enigma

# Scramble-only mode (existing)
enigma scramble --speed 50
```

## Expected Workflow
1. **Setup:** User runs `enigma css-config` to configure
2. **Build:** User builds their project (Next.js, Vite, etc.)
3. **Optimize:** User runs `enigma` to consolidate patterns
4. **Result:** Optimized CSS and rewritten assets, with optional scrambling

# Questions for Clarification

Based on my review of all PRDs, I believe I understand the integration now, but I have a few questions:

## 1. Command Naming and Structure
**Question:** Should the main command be:
- `enigma` (no subcommand) - the primary optimization workflow
- `enigma optimize` - explicit subcommand for optimization
- Keep existing pattern with `css-optimize` as separate command

**From PRDs:** The core PRD suggests `enigma` is the main tool, scramble PRD shows `enigma css-config --scramble`, implying `enigma` is the base command.

## 2. Default Behavior Integration
**Question:** When someone runs `enigma` (main command), should it:
- Always attempt scramble integration if package is detected?
- Require explicit `--scramble` flag for scramble integration?
- Have different default behaviors based on configuration?

**From PRDs:** Scramble PRD shows scramble flags on existing commands, suggesting opt-in behavior.

## 3. Backward Compatibility
**Question:** Do existing commands like `enigma css-config` need to continue working exactly as they do now?
**Assumption:** Yes, based on the established CLI patterns and user expectations.

**My Understanding:** The main `enigma` command should be the core optimization workflow, with existing commands remaining as supporting utilities, and scramble integration should be opt-in via flags.
